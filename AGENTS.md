# AGENTS.md

Generated Motoko client library for the Spotify Web API, distributed as the [mops](https://mops.one) package `spotify-client` for use in Internet Computer canisters.

## Generated code — do not hand-edit

The entire `src/` tree is generated by [OpenAPI Generator](https://openapi-generator.tech) (Motoko client, `org.openapitools.codegen.languages.MotokoClientCodegen`) from Spotify's OpenAPI spec. Do not hand-edit files under `src/`; they are overwritten on regeneration. Behavioral changes belong in the generator/templates and land via "regen" commits (see the git log and `CHANGELOG.md`). `.openapi-generator/FILES` lists every generated path and `.openapi-generator-ignore` controls what regeneration preserves.

## Toolchain

`mops.toml` pins the Motoko compiler: `moc = "1.4.1"` under `[toolchain]`. Use that version; do not bump it as part of unrelated work.

## Build / dependencies

This is a library, not a deployable canister, so there is no build or test script in the repo (no CI workflows, no Makefile, no package scripts). To resolve dependencies for local type-checking:

```bash
mops install
```

Dependencies (with pinned versions) are declared in `[dependencies]` of `mops.toml` and locked in `mops.lock`; edit `mops.toml`, not `mops.lock` by hand. Consumers compile against this package with `moc --check` via mops, so any change must type-check cleanly across every file in `src/`.

## Layout

- `src/Apis/` — one module per Spotify API group (e.g. `SearchApi.mo`, `PlayerApi.mo`). Each operation has a module-level `async*` form and a class-level `async` form.
- `src/Models/` — one module per request/response/enum type.
- `src/Config.mo` — shared `Config` type and `defaultConfig` (base URL, `cycles`, auth, outcall options).

## Conventions

- `mops.toml` `[package].files` controls which paths ship in the published package; keep it in sync when generated output changes.
- `SKILL.md` and `icp.yaml` are consumer-facing helpers (a connector skill and an `icp-cli` deploy recipe, respectively); they document usage and are not part of the library's compiled surface.
- Auth tokens are supplied by the caller at runtime via `Config.auth`; never hardcode credentials.
- `README.md` and `SKILL.md` list every generated Model and API and show usage examples — read them instead of re-deriving the surface.
